# ฐานข้อมูลคุยกับอ้ายโอม

สร้างจริงบน Supabase project `unjtfvxnxdgqlupzkgoc` วันที่ 27 ตุลาคม 2026 ผ่าน migration `create_private_chat_foundation`

## โครงสร้าง

| ตาราง | หน้าที่ |
| --- | --- |
| chat_sessions | ห้องสนทนา ชื่อผู้เข้าชม สถานะเปิด/ปิด และเวลาที่เจ้าของอ่านล่าสุด |
| chat_messages | ข้อความ ผู้ส่ง และเวลา |
| bot_knowledge | คำตอบที่อนุมัติให้บอตใช้ มีข้อมูลเริ่มต้น 7 เรื่อง |
| site_admins | อีเมลเจ้าของที่อนุมัติล่วงหน้า และบัญชีที่ยืนยันตัวตนแล้ว |
| chat_inbox (view) | รายการห้องและจำนวนข้อความผู้เข้าชมที่ยังไม่อ่าน โดยยังเคารพ RLS |

`chat-schema.sql` เป็นสำเนาซอร์สของ schema ที่ใช้สร้างจริง ไม่ต้องรันซ้ำกับโปรเจกต์นี้ ส่วนประวัติ migration เก็บใน Supabase

## สิทธิ์

- เปิด RLS ทุกตาราง
- ผู้เข้าชมต้องมี Supabase Auth session (รองรับ anonymous sign-in เมื่อเปิดใช้ใน Auth settings) และเห็นเฉพาะแชทตนเอง
- ผู้ที่ไม่มี Auth session อ่านได้เฉพาะคำตอบบอตที่เผยแพร่
- สร้างห้องด้วย `chat_sessions.insert({ display_name })` โดย DB กำหนด visitor_id ให้
- ส่งข้อความด้วย `chat_messages.insert({ session_id, body })` โดย DB กำหนด sender_id, sender_role และเวลาให้
- ผู้เข้าชมปลอมเป็น owner/bot หรือแก้ข้อความเก่าไม่ได้
- ผู้เข้าชมส่งได้ไม่เกิน 20 ข้อความต่อนาทีต่อบัญชี (ต้องเพิ่ม CAPTCHA/การป้องกันการสร้างบัญชีจำนวนมากก่อนเปิด anonymous sign-in)
- ข้อความบอตต้องเขียนจาก backend ที่เชื่อถือได้ ห้ามใส่ service role key ในหน้าเว็บ
- เจ้าของเห็นทุกห้อง ตอบได้ ปิดห้อง และตั้ง `last_admin_read_at` เพื่อเคลียร์ unread_count ได้

## บัญชีเจ้าของ

เพิ่มรายการอีเมลที่โอมอนุมัติไว้ใน DB แล้ว แต่ยังไม่มีบัญชี Auth ที่ยืนยันตัวตน จึงยังไม่มีการให้สิทธิ์กับ user_id ใด

หลังสร้างหน้า login:

1. ให้เจ้าของลงชื่อเข้าใช้และยืนยันอีเมลผ่าน Supabase Auth
2. เรียก RPC `claim_chat_owner()` ซึ่งตรวจ email_confirmed_at, บัญชีที่ไม่ใช่ anonymous และอีเมลที่อนุมัติไว้ฝั่ง DB
3. เมื่อ RPC สำเร็จ ค่อยเรียก `is_chat_owner()` ในคำขอถัดไป และโหลด `chat_inbox`

อย่าเลือกเจ้าของจาก user_metadata, คนแรกที่เข้ามา, หรือ flag ใน JavaScript

## การทดสอบ

ใช้ `chat-access-test.sql` ใน transaction ที่ rollback ทั้งหมด ทดสอบผ่านแล้ว:

- การแยกแชทระหว่างผู้เข้าชมสองคน
- การป้องกันปลอมผู้ส่งและเพิ่มสิทธิ์ตนเอง
- บัญชีเจ้าของที่ยังไม่ยืนยันอีเมลถูกปฏิเสธ และบัญชีที่ยืนยันแล้วรับสิทธิ์ได้
- เจ้าของเห็นทั้งสองห้องและตอบกลับได้
- จำนวนข้อความใหม่และการทำเครื่องหมายว่าอ่านแล้ว
- ผู้เข้าชมส่งข้อความเข้าห้องปิดหรือแก้ข้อความเก่าไม่ได้
- จำกัดอัตราการส่งข้อความ
- backend ส่งข้อความบอตได้

หลังทดสอบไม่เหลือบัญชีหรือข้อความทดสอบ และ Supabase security/performance advisors ไม่มีคำเตือน

## งานถัดไป

ฐานข้อมูลพร้อม แต่เว็บไซต์ Netlify ปัจจุบันยังไม่มีหน้าแชทหรือ login ที่เชื่อมฐานข้อมูลนี้ การแจ้งเตือนใน DB เป็นตัวนับใน chat_inbox ยังไม่ใช่อีเมล, LINE หรือ Web Push

ต้องเพิ่มหน้าต่างแชท, บัญชีผู้เข้าชม, หน้า login เจ้าของ และส่วนอ่าน/ตอบใน Dashboard ก่อนใช้งานจริง
